The unglamorous list that decides whether a company or a university can actually deploy this. None of it is interesting and all of it is the difference between a pilot and a rollout.

- **`SECURITY.md`** — where to report, what response time to expect, what is in scope. Its absence is a red flag on every procurement checklist that exists.
- **An SBOM per release**, in CycloneDX or SPDX, generated in CI. Increasingly a contractual requirement rather than a nicety.
- **Signed releases and a reproducible build.** Anyone should be able to rebuild the published artefact and get the same bytes. kosmos is unusually well placed for this — determinism is already a stated property of the engine.
- **A strict Content-Security-Policy** with no `unsafe-inline` and no `unsafe-eval`, documented so a self-hoster can tighten it further rather than having to loosen it.
- **"No data leaves the browser", enforced rather than promised.** A CI test that loads the built application, exercises every module, and fails the build if a single network request is made. The README already makes this claim; a claim that is not tested is a claim that will eventually become false without anyone noticing.
- **Subpath hosting and an air-gapped install guide.** Institutions host things at `/tools/kosmos/` behind a proxy with no outbound access. The build already uses relative paths — write it down and test it.
- **A plain statement of what is stored locally** and a visible way to clear it.
- **A licence audit of every dependency**, published. Legal asks; six dependencies makes this a short document, which is itself an argument.
